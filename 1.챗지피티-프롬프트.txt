# **전보·신규 인사발령통지서 자동화 프로그램 개발 프롬프트**

권장 개발방식: 로컬 웹앱 + Windows EXE 배포

제시한 개발계획을 검토한 결과, **Claude Code의&#x20;**`pm-agent`**로 프로젝트를 설계하고,&#x20;**`html-plan`**&#x20;스킬로 개발계획과 UI 시안을 시각화한 다음,&#x20;**`/goal`**&#x20;워크플로우로 구현·테스트·검증까지 수행하도록 구성**하는 것이 적합합니다.

특히 이번 프로그램은 일반적인 엑셀 문서 병합과 달리 다음 사항이 중요합니다.

- 기존 한글(HWP) 인사발령통지서의 **서식·글꼴·표·여백·결재란 보존**
- 엑셀의 신규·전보 구분에 따른 자동 양식 선택
- 학교명 표준화와 발령일의 정확한 적용
- 개인정보의 외부 전송 및 서버 저장 차단
- 대상자별 HWPX 파일 생성과 일괄 ZIP 다운로드
- 개발이 완료되면 일반 직원도 별도 명령어 없이 실행할 수 있는 프로그램 제공

## **1. 웹앱과 EXE 비교 및 권장 아키텍처**

| 평가항목         | 서버형 웹앱       | 로컬 웹앱    | Windows EXE |
| ------------ | ------------ | -------- | ----------- |
| 사용자 편의성      | 높음           | 높음       | 매우 높음       |
| 개인정보 보호      | 별도 보안 설계 필요  | 우수       | 우수          |
| HWP 원본 서식 보존 | 구현 난도 높음     | 한컴 연동 가능 | 한컴 연동 가능    |
| 설치 편의성       | 별도 설치 불필요    | 실행환경 필요  | 패키징 가능      |
| 오프라인 사용      | 서버 구성에 따라 다름 | 가능       | 가능          |
| 유지관리         | 중앙 관리 용이     | 비교적 용이   | 재배포 필요      |
| 이번 사업 적합도    | 보통           | 매우 높음    | 매우 높음       |

**최종 제안:** Python + 로컬 웹 UI + 한컴오피스 자동화 + EXE 패키징.

우선 로컬 웹앱으로 개발하고, 완성된 애플리케이션을 EXE로 배포하는 2단계 접근을 추천합니다. Python의 FastAPI와 프런트엔드를 결합하거나 PySide6 기반 데스크톱 UI를 사용하는 방법을 비교하도록 하겠습니다.

한컴 공식 기술자료에 따르면 `pyhwpx`는 독립적인 HWPX 파서가 아니라 Windows에 설치된 한컴오피스를 COM 방식으로 제어하는 자동화 라이브러리입니다. 따라서 \*\*한컴오피스 설치 여부와 실제 양식의 변환 결과를 먼저 검증하는 기술검증(POC)\*\*이 중요합니다.&#x20;

## **3. 개발 전 반드시 반영할 보완사항**

| 검토항목    | 현재 계획         | 보완·판단 기준                               |
| ------- | ------------- | -------------------------------------- |
| 발령일     | 엑셀 `임용일` 존재   | 신규·전보 모두 임용일을 발령일로 사용할지 설정 가능하도록 설계    |
| 엑셀 열 구조 | `발령교//구분`     | H열 공란 가능성 확인. `구분`은 실제 I열 우선, 헤더 검증 병행 |
| HWP 양식  | `.hwp` 원본 2개  | HWP → HWPX 변환 및 서식 보존 검증 필요            |
| 치환 필드   | `{{직종}}` 등 5개 | 머리말·표·글상자·본문 안의 치환 가능 여부 확인            |
| 학교명     | 학교명 시트        | 엑셀 명부 우선, 외부 검색은 학교명에 한해 별도 승인         |
| 주민등록번호  | 엑셀에 포함        | 치환에 필요하지 않다면 결과물과 로그에서 제외              |
| 대량 작성   | 1인 1파일        | 중복 파일명 방지·생성결과 검증·재생성 기능 추가            |
| 저장방식    | 서버 저장 금지      | 로컬 임시파일 처리 후 삭제, 외부 API 전송 차단          |
| 원본 보존   | 명시되지 않음       | 원본 엑셀·HWP는 수정하지 않고 출력물만 신규 생성          |

아울러 `html-plan` 공식 스킬은 대화형 HTML 계획서를 생성하고 사용자의 결정사항을 회신받아 반영하는 방식입니다. 중요한 결정이 확정되기 전 실제 구현을 시작하지 않도록 명시되어 있으므로, **계획 승인 단계와&#x20;**`/goal`**&#x20;실행 단계를 분리**하는 것이 정확합니다.&#x20;

# 프로젝트: 교육공무직원 신규임용·전보 인사발령통지서 자동화 시스템

## [0. 최상위 실행 지시]

너는 15년 이상의 경력을 가진 시니어 교육공무직원 인사관리 담당자이자, Windows 업무 자동화·Python·HWP/HWPX 문서 자동화·엑셀 처리·UI/UX 설계 전문 개발자다.

본 프로젝트의 최종 목표는 **전주교육지원청의 신규임용 및 전보 인사발령통지서를 엑셀 데이터에 기초하여 자동 생성하는 실무용 프로그램을 완성하는 것**이다.

다음 작업 방식을 반드시 준수하라.

1. `pm-agent`를 활용하여 전체 프로젝트 계획을 수립한다.
2. `html-plan` 스킬로 개발계획·기술구조·화면 시안·데이터 흐름·사용자 의사결정 항목을 시각화한다.
3. 사용자에게 확인이 필요한 사항은 중요도에 따라 질문하고 구체화한다.
4. 계획 승인 전에는 실제 본개발에 착수하지 않는다. 단, 파일 분석과 읽기 전용 기술검증은 가능하다.
5. 계획 승인 후 `/goal` 워크플로우를 사용하여 개발·테스트·오류수정·최종 검증까지 수행한다.
6. 명칭만 보고 에이전트나 명령어가 존재한다고 가정하지 말고 먼저 설치 여부와 사용법을 확인한다.
7. `pm-agent`나 `/goal`이 설치되어 있지 않다면 사용 가능한 대체 워크플로우를 제안하고, 필요한 경우 프로젝트 전용 명령어를 생성한다.
8. 단순 시제품이 아니라 실제 교육지원청 인사담당자가 사용할 수 있는 완성된 프로그램을 목표로 한다.

## [2. 데이터 구조 분석]

### 2-1. 엑셀 구조

헤더는 1행이고 인사발령 대상자 정보는 2행부터 시작한다.

| 열 | 내용           |
| - | ------------ |
| A | 순            |
| B | 직종           |
| C | 성명           |
| D | 주민등록번호       |
| E | 임용일          |
| F | 현임교          |
| G | 발령교          |
| H | 공란 또는 기타 데이터 |
| I | 구분           |

반드시 실제 엑셀을 분석하여 열 위치를 확인한다.

헤더명과 열 번호가 다르면 사용자에게 알려주고, 자동 열 매핑을 제안한다.

주민등록번호는 이번 양식의 필수 치환 항목이 아니므로 기본적으로 사용하지 않는다. 애플리케이션 화면, 오류로그, 디버그 출력, 결과파일 이름에도 노출하지 않는다.

### 2-2. 인사 구분

I열 `구분` 값을 기준으로 다음과 같이 처리한다.

- `신규` → 신규임용통지서 양식
- `전보` → 전보인사발령통지서 양식

대소문자, 앞뒤 공백, 눈에 보이지 않는 공백을 정규화한다.

`신규`, `전보` 외의 값은 임의로 분류하지 말고 검증 오류로 표시한다.

엑셀에서 유효한 데이터 1행은 대상자 1명에 해당한다.

따라서 대상자 1명당 HWPX 파일 1개를 생성한다.

### 2-3. 발령일 처리

기본 발령일은 엑셀 E열의 `임용일`로 설정한다.

단, 실제 인사행정에서 임용일·전보일·통지서 발령일이 다를 수 있으므로 다음 옵션을 제공한다.

- 엑셀 임용일을 사용
- 전체 대상자에게 동일한 발령일 적용
- 대상자별 발령일 직접 수정

날짜가 날짜형·문자열·엑셀 일련번호 등으로 입력된 경우 이를 정확하게 해석한다.

최종 출력 날짜 형식은 원본 서식에 맞춘다.

## [3. 한글 문서 자동생성 엔진]

### 3-1. 기존 HWP 양식 분석

두 HWP 원본 파일을 실제로 열어 다음 항목을 분석하라.

1. 페이지 수 및 용지 방향
2. 용지 크기 및 여백
3. 글꼴과 글자 크기
4. 문단 간격과 줄 간격
5. 표의 행·열·테두리
6. 문서 내 그림 및 도장
7. 글상자·머리말·꼬리말
8. 치환 대상의 정확한 위치
9. 치환 후 줄바꿈 및 페이지 넘침 가능성
10. 한컴오피스 버전과 HWPX 저장 호환성

원본을 절대로 수정하거나 덮어쓰지 않는다.

### 3-2. HWPX 출력

입력양식은 `.hwp` 또는 `.hwpx`를 지원한다.

출력파일의 기본 형식은 `.hwpx`로 한다.

다음 기술을 검토하라.

- 한컴오피스 Windows COM 자동화
- pywin32
- pyhwpx
- HWPX XML 기반 치환
- 기타 검증 가능한 HWPX 문서 처리 방식

기술별 서식 보존도, 설치 의존성, 속도, 오류 복구, 대량 처리 안정성을 비교하라.

원본 HWP가 복잡한 서식이라면 실제 한컴오피스를 통한 자동화를 우선 검토한다.

단순 텍스트 추출 방식으로 문서를 새로 조립하여 원본 서식을 잃어버리는 방법은 채택하지 않는다.

### 3-3. 치환 필드

다음 위치에 실제 엑셀 내용을 입력한다.

- `{{직종}}` → B열 직종
- `{{성명}}` → C열 성명
- `{{발령일}}` → E열 임용일 또는 사용자가 지정한 발령일
- `{{현임교}}` → F열 현임교
- `{{발령교}}` → G열 발령교

각 양식별로 실제 존재하는 플레이스홀더를 검사한다.

원본 양식에 플레이스홀더가 없는 경우 이를 자동으로 만들어졌다고 가정하지 말고 사용자에게 보고한다.

치환 문자열이 여러 XML 텍스트 노드로 나뉘어 있거나 표·글상자 등에 포함된 경우에도 정확하게 처리할 수 있는지 검증한다.

전보통지서에 현임교가 필요하지만 신규통지서에는 필요하지 않을 수 있으므로 양식별 필수항목을 구분한다.

치환 이후에도 원본 서식이 보존되어야 한다.

### 3-4. 출력 파일명

다음 파일명 규칙을 제안한다.

신규:

`2027.03.01_신규_조리실무사_홍길동_전주가람초등학교.hwpx`

전보:

`2027.03.01_전보_교무실무사_김철수_전주나래초등학교.hwpx`

날짜와 학교명은 실제 데이터로 대체한다.

동명이인이 있거나 파일명이 중복되면 고유번호를 추가한다.

동명이인을 서로 다른 인사대상자로 식별할 수 있도록 원본 행 번호 및 내부 고유 식별자를 관리한다.

## [4. 학교명 정규화 엔진]

### 4-1. 기준자료

엑셀파일에 `학교명` 시트가 있으면 이를 학교명 표준화의 우선 기준으로 활용한다.

학교명 시트의 실제 헤더와 구조를 분석한다.

다음과 같은 표기를 정규화한다.

예시:

`전주가람초` → `전주가람초등학교`

단, 이러한 매핑은 실제 학교명 시트에서 확인되는 경우에만 확정한다.

동일하거나 유사한 학교명이 여러 개 존재하는 경우 자동 확정하지 않는다.

### 4-2. 학교명 처리 순서

1. 엑셀 학교명 시트와 정확히 일치하는지 확인
2. 별칭·약칭 매핑 확인
3. 공백·괄호·특수문자 차이 검사
4. 높은 신뢰도의 단일 후보가 있으면 자동 적용
5. 모호한 후보는 사용자 선택 요청
6. 기준자료에 없는 학교는 별도 검증 목록 생성

### 4-3. 전주 외 지역

전주 외 지역 학교가 존재할 경우 다음 방식 중 선택하게 한다.

- 사용자가 공식 학교명을 직접 입력
- 사용자가 제공한 학교명부 추가
- 외부 학교정보를 검색하여 후보 제안

인터넷 검색은 기본적으로 비활성화한다.

외부 조회가 필요한 경우 사용자의 별도 승인을 받은 후 학교명 또는 기관명에 한해서만 검색한다.

성명, 주민등록번호, 인사이동 내역, 개인별 발령정보는 외부 검색엔진이나 외부 API에 전송하지 않는다.

외부 검색결과는 공식 학교정보와 비교하고, 검증되지 않은 이름은 자동 확정하지 않는다.

정규화 내역은 사용자에게 보여준다.

## [5. 개인정보 보호 및 보안]

본 프로그램은 교육공무직원 인사자료를 처리하는 내부 업무 도구다.

다음 원칙을 준수하라.

1. 모든 개인정보 처리는 사용자 PC 내부에서 수행한다.
2. 원격 서버를 구축하지 않는다.
3. 원본 파일을 클라우드에 업로드하지 않는다.
4. 외부 분석 API·원격 AI API를 호출하지 않는다.
5. 인터넷 연결 없이 주요 기능을 사용할 수 있어야 한다.
6. 파일 처리용 임시 디렉터리는 로컬 PC에 생성한다.
7. 작업 종료 또는 오류 발생 시 임시 개인정보 파일을 정리한다.
8. 결과물은 사용자가 지정한 로컬 경로에 저장한다.
9. 로그에는 주민등록번호 및 민감한 인사정보를 기록하지 않는다.
10. 디버그·오류 보고 시 개인식별정보를 마스킹한다.
11. 외부 텔레메트리나 자동 오류 전송 기능을 기본 비활성화한다.
12. 파일 경로 접근권한과 결과물 저장폴더 보안을 검토한다.

개발 단계에서 실자료를 사용한 외부 네트워크 전송 테스트를 금지한다.

## [12. 자가 검증 및 품질 기준]

각 Phase가 끝날 때 다음 다섯 관점으로 검토한다.

**인사업무 관점**

- 인사발령 대상자가 누락되지 않았는가?
- 신규와 전보가 정확히 구분되었는가?
- 학교명과 발령일이 정확한가?

**문서 품질 관점**

- 원본 양식이 보존되었는가?
- 모든 치환 필드가 정상 적용되었는가?
- 페이지가 잘리거나 표가 깨지지 않았는가?

**보안 관점**

- 개인정보가 외부에 전송되지 않는가?
- 불필요한 개인정보가 로그에 남지 않는가?
- 원본 파일이 안전하게 보존되는가?

**소프트웨어 관점**

- 오류 발생 시 안전하게 복구되는가?
- 대량 인원 처리 시 안정적인가?
- Windows PC에서 실행 가능한가?

**사용자 경험 관점**

- 비전문가도 사용할 수 있는가?
- 오류 위치와 수정방법이 명확한가?
- 생성 결과를 손쉽게 확인할 수 있는가?

**STEP 2.** 작업폴더의 엑셀·HWP 원본 파일을 읽기 전용으로 분석한다.

**STEP 3.** pm-agent로 전체 프로젝트 계획을 수립한다.

**STEP 4.** html-plan 스킬로 대화형 HTML 개발계획 및 세련된 공공기관 UI 시안을 생성한다.

**STEP 5.** 사용자 결정이 필요한 중요한 항목을 정리하여 질문한다.

**STEP 6.** 사용자의 회신을 계획에 반영하고 승인받는다.

**STEP 7.** 승인된 계획에 따라 /goal 워크플로우로 본개발을 수행한다.

**STEP 8.** 모든 기능을 테스트하고 발견된 오류를 수정한다.

**STEP 9.** 실행파일과 사용설명서를 작성한다.

**STEP 10.** 최종 결과물과 테스트 결과보고서를 제공한다.

사용자 승인을 받은 후에는 이미 확정된 내용을 반복해서 질문하지 않는다.

단, 개인정보 처리방식의 변경, 외부 전송, 원본 데이터 변경, 인사발령 내용에 영향을 주는 중대한 변경은 별도 승인을 요청한다.

지금은 **STEP 1부터 STEP 5까지 진행**하라. 계획 승인을 받기 전 본개발에 들어가지 마라.
